# Main Agent Proposal-to-Project Workflow

## Overview

A Proposal is a persistent discussion record, not a Project. Main Agent creates and saves a draft, discusses and revises it with the Product Owner, then prepares a pre-project Team Plan using the registered Specialist Agent catalog. The Product Owner's single formal confirmation creates the Project row. Task decomposition, task assignment and Specialist execution are deliberately deferred to the next release.

## Lifecycle

1. `discussion` — Proposal saved with a backend-generated Proposal ID. Requirements, objective, scope, deliverables, milestones, timeline, budget assumptions, risks and acceptance criteria may be refined.
2. Team Plan `draft` — Main Agent proposes workstreams and registered Specialist candidates. The backend validates Agent existence/enabled status, model availability, Capability availability, Tool registration/enabled status and Agent Tool permissions.
3. Team Plan `owner_approved` — Set by the Product Owner's final formal project confirmation (or recorded earlier through the optional Team Plan review endpoint). Any Proposal revision marks the previous Team Plan `stale`.
4. `approved` / lifecycle `formal_project_approved` — Formal confirmation creates one row in `sys_projects`, links it to the Proposal, stores the approved baseline and materialises the initial Project Prompt. It creates no `sys_tasks` rows and no `sys_task_assignments` rows.
5. Execution remains unauthorised. Task decomposition, task assignment and Specialist dispatch belong to the next release and require separate execution authorisation.

## Chat commands

Use the backend-returned Proposal ID:

- `plan team for proposal <proposal-id>` — generate or regenerate the pre-project Team Plan.
- `formally approve proposal <proposal-id>` — final Product Owner confirmation; creates the Project only if the Team Plan is current and all validation gaps are clear.
- `reject proposal <proposal-id>: <reason>` — reject the Proposal.
- `request changes for proposal <proposal-id>: <comment>` — record requested changes; revise the same Proposal during discussion.

The Main Agent may use the `revise_project_proposal` tool during an ongoing discussion. A revision invalidates the previous Team Plan approval and requires a new analysis.

## API

- `POST /api/v1/proposals` — save a discussion draft and return the real Proposal ID.
- `GET /api/v1/proposals` — list saved Proposals; optional `status` filter.
- `GET /api/v1/proposals/{proposal_id}` — retrieve a Proposal.
- `PATCH /api/v1/proposals/{proposal_id}` — revise a Proposal before formal approval.
- `POST /api/v1/proposals/{proposal_id}/team-plan/analyze` — generate a Proposal-level Team Plan before a Project exists.
- `GET /api/v1/proposals/{proposal_id}/team-plan` — retrieve the Team Plan.
- `POST /api/v1/proposals/{proposal_id}/team-plan/approve` — optional explicit Team Plan review record.
- `POST /api/v1/proposals/{proposal_id}/formal-approval` — formally create the Project.
- `POST /api/v1/proposals/{proposal_id}/decision` — reject or request changes; legacy approval-in-principle support remains for compatibility.

## Formal creation guarantees

- Proposal IDs are generated by the backend and persisted in `sys_project_proposals`.
- Project creation requires a current Team Plan with at least one workstream and one ready registered Specialist, with no unresolved Capability, Agent, model, Tool or permission gaps.
- Formal creation and the Proposal-to-Project link are committed in the same SQLite transaction.
- Repeating formal approval returns the already-created Project rather than creating a duplicate.
- The approved Proposal snapshot is retained in `approved_baseline_json`.
- The Team Plan is copied into the project-scoped Team Plan store for later project management visibility.
- Formal project creation does not create tasks, task dependencies, task assignments, or start execution.

## Current scope and limitations

This release connects Proposal discussion, Proposal revision, pre-project Team Planning and formal Project creation. The proposal-level Team Plan uses the Main Agent LLM and deterministic registry/model/Tool/permission validation. Configuration gaps must be fixed in Agent, Model, Capability or Tool management and the Team Plan regenerated. Task decomposition, task assignment, Specialist execution, live issue reporting, Main Agent operational decisions and Product Owner escalation are next-release work.
